# ATRO Mobile Platform Experience

## Goal

Make every ATRO web journey usable and coherent on phones, while preserving the distinct needs and permissions of Kenyan clients, diaspora clients, the office team, and the owner. This is a responsive-web plan, not a separate native app.

## Product and design guardrails

- Keep role-specific information architecture: owner = portfolio decisions; office = daily operations; Kenyan client = practical progress and next actions; diaspora client = remote evidence, decisions, and payment confidence.
- Preserve existing URLs, account access rules, and desktop behavior. Do not solve mobile problems by hiding important content or shrinking desktop layouts.
- Design for touch, one-handed use, interrupted sessions, small screens, and variable network quality. Use clear labels and status text, not color or icons alone.
- Treat fixed headers, bottom navigation, chat/WhatsApp controls, dialogs, and safe areas as one layout system so content and actions are never obscured.
- Follow `.agent/skills/plan-writing/SKILL.md`, `.agent/workflows/ui-ux-pro-max.md`, and `.agent/agents/frontend-specialist.md`; use `ROLES.md` as the dashboard product contract.

## Shared acceptance criteria

- Check 375, 390, and 430px phone widths, plus 768, 1024, and 1440px regression widths; use current supported browser tooling for mobile Safari and Android Chrome where available.
- No unintended horizontal scrolling, clipped text/actions, keyboard-covered fields, or content hidden behind headers, bottom nav, chat, or WhatsApp controls.
- Primary touch targets meet the project’s `.agent` mobile guidance (aim for at least 48px); focus is visible; dialogs and navigation remain keyboard accessible.
- Loading, empty, offline/slow, validation, and error states are designed—not just the happy path. Long lists and tables have a deliberate mobile presentation.
- Public content remains public and generic; private project data remains account-scoped. Kenya/diaspora destinations and owner/office/client permissions do not change.
- Each phase is reviewed on actual routes before moving to the next role family; avoid a single end-of-project responsive CSS pass.

## Dependencies and rollback

M1 establishes the baseline. M2 is the shared prerequisite for route work. M3–M5, M6–M7, and M8 can proceed as separate vertical slices after M2, but M6/M7 should share components only where behavior is genuinely shared. M9 is always last.

Keep changes route-scoped and incremental. If a shared-shell adjustment breaks another route or desktop behavior, revert that specific adjustment and address the affected screen locally before proceeding.

## Done when

- All public, conversion, client, office, and owner route families have passed the shared acceptance criteria.
- All four user seats remain distinct and their mobile navigation, actions, and redirect destinations are correct.
- No high-impact baseline issue remains unresolved; any deferred lower-priority issue is documented with route, impact, and follow-up.
- Typecheck, lint, relevant tests, production build, and the completed mobile route matrix pass.

## Implementation status — 2026-11-07

- Shared navigation and dashboard drawers were checked for keyboard open/close, focus return, and scroll-lock cleanup. The public mobile menu and client dashboard entry targets are at least 48px.
- A 38-route smoke matrix was run at 375, 390, 430, 768, 1024, and 1440px. It found no missing visible page headings or persistent page overflow. An initial Kenyan-portal overflow reading was transient and did not reproduce after the portal settled; both client portal guest previews subsequently passed all six widths.
- Kenyan and diaspora guest-preview portals were checked for mobile section switching and drawer behavior. These previews are read-only; payment, approval, decision, and other account actions were not performed.
- A local-development-only persona switcher opens the owner, office, Kenyan client, and diaspora client workspaces without accounts. It uses PGLite fixtures only when `DATABASE_URL` is unset; local workspace actions operate on those fixtures. Payment-provider calls and external notification delivery remain disabled locally.
- Owner and office dashboards were smoke-checked at a 360px CSS viewport with no horizontal overflow. This verifies layout and local fixture workflows, not real-account permissions.
- Public enquiry validation/review, diaspora return context, service details, BOQ interaction, material search/filtering, county search/detail, and tool routes were exercised on mobile. No real enquiry was submitted.
- Real-account permission checks, Mobile Safari/Android checks, and a clean full `npm test` run remain outstanding.
- Typecheck, targeted lint/format, focused tests, and production build have passed during this implementation. The full test suite has known environment/baseline failures, including missing `.grok/skills/og` files, Windows symlink permission errors, and Open Graph assertions.
